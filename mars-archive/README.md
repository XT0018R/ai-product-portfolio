## 这个产品解决什么问题

华晨宇十年演唱会的「舞台形态 / 场次 / 歌单」散落各处、且常被误传（例如把普通四面台说成"火星乐园 2.0 永久基地"）；粉丝想回顾某场找不到准确信息，想分享现场记忆也没有统一阵地。这个产品做一个「权威 + 可共创」的火星演唱会档案馆——既能查每场准确信息，又能由歌迷共同书写记忆（现场照片 + 火星小故事），形成 UGC 闭环。

## 核心功能

- 演唱会数据检索：87 场正式演唱会结构化（年份 / 城市 / 场馆 / 舞台形态 / 歌单 / 新歌首唱 / 现场视频），手机端可访问
- UGC 回忆墙：上传照片、写「火星小故事」，本地保存 + 可选同步全局共享
- 数据权威性把关：只收正式演唱会，剔除混入的特别活动，保证档案「权威感」而非大杂烩

## 为什么这样做（产品决策）

- **用户痛点 → 方案**：我观察到演唱会信息散落且常被误传、粉丝记忆无处安放，因此选择「官方信息整合 + 个人回忆存放」的双层定位，UGC 只是附加价值，不做成内容社区。
- **取舍**：在「做大而全的社区」和「做权威可信的档案」之间优先了后者，因为粉丝的核心诉求是"查得准、找得到"，而不是"刷不完的信息流"。
- **数据/验证**：87 场 / 24 城 / 20 省真实数据已结构化上线，覆盖 11 年演唱会历程；为回忆墙加纯文字「火星小故事」条目，让记忆有温度、也降低 UGC 门槛。
- **工程方式**：采用 Vibe Coding 快速验证产品形态，并做前端降级探测，保证在弱网或低端设备上仍可访问，优先覆盖"手机随手打开"这一真实使用场景。

## 技术架构

- 前端：响应式页面，支持手机访问
- 数据层：87 场演唱会结构化数据 + UGC 内容存储
- 工程方式：Vibe Coding 迭代开发，前端降级探测保证可用性
- 数据产品思维：结构化字段设计（年份 / 城市 / 场馆 / 舞台形态 / 歌单 / 新歌首唱 / 现场视频）

## 如何运行

```bash
# 1. 安装依赖
npm install

# 2. 配置环境变量（复制 .env.example 为 .env 并填写）
cp .env.example .env

# 3. 启动开发服务
npm run dev
```
