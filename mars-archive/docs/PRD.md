一句话定位

一个属于「火星人」自己的演唱会档案馆：把分散在各平台的巡演信息、歌单、造型、足迹与回忆，系统梳理成一份可随时回看、可跨设备存放的个人档案。

  * 回忆墙支持**跨设备共享** （16 台设备足迹已打通）
  * 静态 Web 形态，**秒开 + 离线可用**

## 01背景与问题定义

华晨宇（粉丝自称「火星人」，官方应援物为「能量棒」）自 2013 年起巡演跨度十余年、城市数十座。粉丝在追现场时普遍面临三类「信息散、回忆散」的痛点，却长期没有一款产品解决——现有内容几乎都集中在「看别人拍的现场」（B 站、微博二创），而「属于自己的那份档案」始终是空白。

### 待解决的核心问题（Problem Statement）

  * **信息分散、无统一梳理：** 同一场次的歌单、舞台形态、巡演脉络散落在 B 站、微博、票务与粉丝笔记中，跨年跨城后很难还原「完整的一夜」。
  * **缺乏系统视角：** 87 场演唱会的年度巡演章、舞台演进（四面台 / 火星乐园 / 星环）、新歌首唱节点，没有一条时间线能把它们串起来。
  * **回忆无处存放：** 自己拍的现场照、散场后的心情文字，散落在不同设备与相册，换手机即丢失，更无法跨设备携带。
  * **「别人的内容」过剩、「自己的档案」稀缺：** 消费他人现场的内容极多，但「给自己一个存档与回忆的存放处」这一需求长期未被满足。

## 02目标用户与用户洞察

### 核心用户画像

**「追巡演的火星人」** ——有 3 场以上现场经历、重视「参与感与纪念意义」的粉丝。她们要的不是「再刷一遍别人剪的现场」，而是「我也在场的证据与回忆」。

### 关键洞察

  * 对粉丝而言，**「我去了哪几场、我拍了什么、我当时什么心情」** 比「别人拍得多好」更有长期价值。
  * 准确率即信任：歌单错一个字、舞台形态说错，都会直接摧毁档案的可信度。
  * 移动端 + 微信是主场景；跨设备（手机 / 平板 / 换机）携带回忆是硬需求。

## 04产品定位与核心价值主张

定位铁律：档案馆 ≠ 内容消费平台

火星档案馆**不是为了「看别人拍的现场」** ——别人拍的现场去 B 站搜就有。它的核心价值是三件事：

① **官方信息的整合** ；② **一整个场次的系统梳理** ；③ **给自己一个存档 / 回忆的存放之处** 。

UGC（回忆墙）定位：自己的回忆存放处，共享是加分项

回忆墙首先是**自己的回忆存放处** ；「顺便能和别人共享」是 best bonus，**但绝不是为了「看别人的」** 。这一条直接决定了对「排行榜、他人内容流」等功能say no，避免产品跑偏成又一个内容消费社区。

## 06核心模块设计

### 6.1 时间轴与年份导航 交互骨架

以「年」为锚点串联全部场次，是整站的信息骨架。宽屏采用**竖排年份导航** ，移动端切换为**横排年份导航** 。导航的滚动跟随手感经历多轮打磨：从最初的离散跳变 / 卡顿，迭代为**连续平滑跟随 + 居中高亮 + 首尾可居中** ，保证长列表下定位始终舒适。

### 6.2 场次档案（Sheet） 系统梳理的落点

点开任意场次，进入该场的系统档案：歌单（歌迷整理、标注「非官方」）、**新歌首唱区** （只保留歌名框，不给解释——歌迷都懂，多余文字反显啰嗦）、造型、照片与火星故事。所有信息围绕「还原完整一场」组织。

### 6.3 造型档案（Looks） 准确性优先的取舍

每场不同造型是粉丝重要记忆点。初版尝试**自动扒取官方微博照片** ，但持续出错（日期两种格式错配、混入非本人图、2724 张中仅 799 张下载成功），反复返工。最终**改为手动拖图的管理后台** ——用「人工校准」换「准确性」，宁可慢、不可错。

### 6.4 足迹地图 从色块到地图

最初用方框 / 色块表示去过的城市，不直观。迭代为**中国地图 + 省份密度着色** ，地理记忆一目了然。该模块曾尝试与「我的足迹」做联动，做出后观感不佳，**当日即止损撤回** （见第 7、11 章）。

### 6.5 回忆墙 / 我的火星（UGC） 回忆的存放与共享

这是产品「给自己存放回忆」定位的实体承载。初版仅支持**照片** ，PM 基于自身粉丝视角判断「仅图不足以承载回忆」，遂加入**火星故事（纯文字心情）** ；统计维度从原本「各场到场火星人排行」改为**人数 / 照片 / 故事三块** ——因为不公开的数据用户并不知道、排行也无意义。共享是加分项：照片与故事可跨设备汇聚到同一面墙。

## 07关键产品决策与取舍

以下每一项都是「做了 vs 没做 / 这样 vs 那样」的主动判断，是面试中最能体现 product sense 的部分。

收录边界：只收正式演唱会，非演唱会活动不入库

保证档案的「纯粹性」与口径一致。演唱会特别活动（非巡演场次）一律不录入，避免数据口径混乱、稀释「档案馆」的专业感。

「看别人」vs「存自己」：明确 UGC 是自己的存放处

拒绝做成内容消费社区。因此砍掉「各场到场人数排行」「他人内容流」等诱惑性功能，聚焦「我去了哪、我拍了什么、我写了什么」。

准确性 > 完整度速度：歌单绝不臆造

歌单数据由歌迷整理，标注「仅作为记录，非官方歌单」；空缺就留空待补，**宁可空着也绝不编造一首歌名** 。这是档案可信度的生命线。

静态优先 + 双层容灾：海外后端不稳也不能「全 0」

当云端（海外 Supabase）超时导致回忆墙拉空时，不显示空白，而是回退到**静态精选档案 + 本机缓存** 双层，保证「永远打得开、至少看到自己 / 已同步的内容」。

需求止损：地图 × 足迹联动做出来嫌丑，当日撤回

投入做出联动效果后，因观感不达标果断回滚，不将就上线。体现「宁可不做、不做半成品」的取舍纪律。

## 08数据策略与准确性治理

档案馆的可信度 100% 取决于数据准不准。我们建立了一套从「录入」到「审计」的治理闭环：

  * **单一事实源：** 全部场次 / 歌单数据集中维护，避免多副本漂移。
  * **歌单标注非官方：** 页面显式标注「仅作为记录，非官方歌单」，管理用户预期、规避误导。
  * **全量审计流程：** 对 170+ 唯一歌名**逐首对照华晨宇真实曲库（维基 discography、百度百科、文旅审批歌单、饭拍视频）核验** ，区分「真实歌曲 vs OCR 垃圾」，统一修正错字与英文大小写（如 `For Forever` / `Here We Are` / `Poker Face`），删除无据片段（如误识别的「好婚」），保留初看像错字实为真实曲目的歌（如《癌》《巨鹿》《河》《荒野魂斗罗》）。
  * **术语规范：** 舞台形态统一用「家舞台」（禁用「甲舞台」）；粉丝海洋称「火海」（呼应火星 + 能量棒文化，禁用「星海」）。

## 09技术方案概要（PM 视角）与容灾设计

### 架构形态

  * **静态前端（零构建）：** 纯 HTML/CSS/JS，无编译链路，运维成本极低、加载极快，易于静态托管。
  * **本地优先（localStorage）：** 用户的照片与故事优先存本机，离线可用、隐私可控。
  * **云端共享（Supabase 免费层）：** 负责跨设备汇聚——足迹（attendance）与共享照片 / 故事（photos）。
  * **静态托管 + 强刷机制：** 部署于静态平台；针对微信跨端强缓存，设计强制刷新参数，避免用户看到旧版本。

容灾设计：双层兜底，拒绝「全 0」

回忆墙首屏直接渲染**内嵌的静态精选档案** （零网络依赖、秒开）；后台再静默拉云端合并。即便海外后端抖动 / 超时，用户看到的是「自己的内容 + 已同步内容」，而非空白墙。该设计在一次真实的海外超时事故后固化，是可用性优先原则的体现。

## 10微信生态适配与分享

  * **跨端强缓存：** 微信内打开易命中强缓存看到旧版，已设计**强制刷新机制** 确保用户拿到最新。
  * **分享头图：** 初始横图被裁剪失真，改为 **1:1 正方形** 分享卡，保证转发观感。
  * **文案规范：** 所有面向用户的文案贴合火星文化（能量棒 / 火海），避免生硬或越界的用词。

## 11项目演进复盘：从 0 到 1 的真实路径

本章为面试核心素材——不讲「我多厉害」，讲「我怎么发现问题、怎么拐弯、怎么解决」。每条都对应上文某个决策的真实来由。

造型模块：自动扒取 → 反复出错 → 改人工后台

先尝试自动抓取官方微博照片，持续踩坑（日期两种格式错配、混入非本人图、2724 张仅 799 张成功）。PM（自身即核心用户）厌烦反复出错，转而建设**手动拖图的管理平台** ，用人工校准保障准确性。→ 对应决策「准确性 > 速度」。

足迹地图：方框色块 → 中国地图密度着色

初版用方框 / 色块表示城市不直观，迭代为省份密度着色的真实地图，地理记忆一眼可辨。

回忆墙：含「排行」 → 删掉 → 改三块统计

最初含「各场到场火星人排行」，PM（核心用户视角）指出不公开数据无从得知、排行无意义，遂删除，改为**人数 / 照片 / 故事** 三块统计。→ 对应「看别人 vs 存自己」定位。

我的火星 / UGC：只有照片 → 加文字故事

PM 判断仅照片不够表达，补充**火星故事（纯文字心情）** ，让回忆从「图」扩展到「图文」。

时间轴：补「新歌首唱」区

后续新增新歌首唱节点，只保留歌名框、不给解释——尊重歌迷认知、保持界面克制。

导航栏：竖排 / 横排双形态 + 滚动手感打磨

宽屏竖排年份、移动横排年份；滚动跟随从离散跳变 / 卡顿，打磨为连续平滑 + 居中高亮 + 首尾可居中。

早期数据 bug：场次 / 歌单不准 → 反复校对 → 铁律「绝不臆造」

初期场次信息、歌曲歌单不准，经多轮校对建立准确性铁律，并沉淀出第 8 章的全量审计流程。

微信生态：强缓存 → 强制刷新；横图头图 → 1:1 方形

针对微信场景的两个真实坑，逐个修掉，保证分享与打开体验。

可用性 pivot：海外超时 → 回忆墙全 0 → 静态 + 缓存双层

一次 Supabase 海外超时导致回忆墙全空白，推动「静态精选档案 + 本机缓存」双层容灾固化。→ 对应第 9 章容灾设计。

需求止损：地图 × 足迹联动做出后嫌丑 → 当日撤回

联动效果做出后因观感不达标果断回滚，不将就。→ 对应决策「需求止损」。

质量工程（持续）：歌单全量审计 + 跨设备同步修复

上线后持续做准确性与可靠性治理：① 对 170+ 歌名逐首网络核验、修正 30+ 错名、清理 OCR 垃圾；② 修复跨设备同步——原拉取逻辑串行叠加超时必输竞速、退回过期快照，改为并行拉取后稳定胜出，新共享的足迹 / 故事得以跨设备出现。

## 12成果与未来展望

### 已达成

  * 87 场正式演唱会 100% 系统录入，歌单经全量审计**零假名、零臆造** 。
  * 时间轴 / 造型 / 足迹地图 / 回忆墙五大模块闭环，定位清晰不跑偏。
  * 回忆墙跨设备共享打通（多设备足迹已汇聚），并在海外超时下仍可降级可用。
  * 微信场景适配（强刷、1:1 分享卡）完成。

### 可延展方向（面试「你还会怎么迭代」）

  * **共享治理：** 引入轻量管理后台，对 UGC 做审核 / 撤回，保障档案调性。
  * **移动端深化：** 继续打磨移动端回忆墙与上传体验，降低「写故事 / 传照片」的摩擦。
  * **数据可移植：** 支持用户导出自己的档案（照片 + 故事），强化「这是我的回忆」的所有权感。
